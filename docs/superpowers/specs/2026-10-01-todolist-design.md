# 할 일 관리 앱 — 설계 문서 (PRD)

작성일: 2026-10-01 (KST)
상태: 승인됨 — 구현 계획 작성 대기

## 1. 목적과 범위

개인이 하루 10~20개 규모의 할 일을 관리하는 웹 앱. 브라우저에서 단독 실행되며
새로고침·브라우저 재시작 후에도 데이터가 유지된다.

사용자는 단 한 명(앱 소유자 본인)이다. 동기화, 계정, 공유, 다중 기기는 범위 밖이다.

### 목록의 수명 (확정)

**날짜 필드 없는 하나의 누적 목록이다.** 할 일은 "오늘 할 일" 같은 날짜 단위로
묶이지 않고 단일 목록에 계속 쌓인다. 날짜 이동 UI, 어제 미완료 항목의 이월
규칙, 마감일 필드는 모두 없다.

**완료한 할 일은 자동으로 사라지지 않는다.** 목록에 그대로 남고 필터로
숨겨진다. 기간 기반 자동 정리는 넣지 않는다. 정리는 사용자가 개별 삭제하거나
'완료 항목 비우기'(6장)를 누를 때만 일어난다.

### 성공 기준

1. 할 일을 추가·수정·삭제·완료 체크할 수 있다.
2. 새로고침 후에도 모든 데이터가 그대로 남아 있다.
3. 전체 및 카테고리별 진행률을 한 화면에서 확인할 수 있다.
4. 10~20개를 연속으로 입력하는 동작이 끊기지 않는다 (Enter 입력, 포커스 유지).
5. 번들러·패키지 매니저·빌드 단계 없이 `index.html` 하나를 열면 동작한다.

### 범위 밖 (명시적 비목표)

반복 할 일, 마감일, 알림, 우선순위, 하위 작업, 태그, 검색, 되돌리기(undo),
로그인/계정, 서버 동기화, 다중 기기 동기화, 카테고리 추가/삭제, 다크 모드 토글,
데이터 내보내기/가져오기.

**사용자가 조작하는 정렬은 없다** (드래그로 순서 바꾸기, 정렬 기준 선택 UI).
단, 목록을 그리려면 어떤 순서든 필요하므로 고정 표시 순서는 3장에 정의되어
있다 — 미완료는 추가순, 완료는 최근 완료순.

## 2. 기술 선택

**단일 HTML 파일.** `index.html` 하나에 HTML·CSS·JavaScript를 전부 인라인한다.
파일을 더블클릭하면 `file://`로 바로 열려 동작하며, 로컬 서버가 필요 없다.

이 선택의 대가를 명시한다: ES 모듈로 파일을 분리하면 로직을 Node 내장 테스트
러너로 단위 테스트할 수 있으나, `file://`에서 CORS 정책 때문에 모듈 로드가
막혀 로컬 정적 서버가 필요해진다. 더블클릭 실행을 우선해 단일 파일을 택했고,
그 결과 Node 단위 테스트는 불가능하다. 대신 7장의 인페이지 테스트 패널로
순수 로직을 검증한다.

의존성 없음. 프레임워크 없음. 빌드 없음.

## 3. 데이터 모델

localStorage 키: `todolist.v1`

```js
{
  version: 1,
  todos: [
    {
      id: "mg3k2a_x7f9q",      // Date.now().toString(36) + "_" + 랜덤 5자
      text: "PRD 초안 검토",    // trim 후 1~200자
      category: "work",        // "work" | "personal" | "study"
      done: false,
      createdAt: 1759280000000,
      completedAt: null        // done=true 로 바뀐 시각, 아니면 null
    }
  ]
}
```

### 결정 사항

**카테고리는 영어 키로 저장하고, 화면 라벨은 코드 상단 상수 맵에 둔다.**

```js
const CATEGORIES = {
  work:     { label: "업무", color: "#2563eb" },  // 파랑
  personal: { label: "개인", color: "#16a34a" },  // 초록
  study:    { label: "공부", color: "#9333ea" }   // 보라
};
```

배지는 이 색을 글자색으로 쓰고 배경은 같은 색의 연한 틴트로 둔다 (색 위에 흰
글자를 얹는 방식보다 목록에서 덜 시끄럽다). 라벨이나 색을 바꿀 때 저장된
데이터를 마이그레이션하지 않아도 된다. 카테고리는 이 세
개로 고정하며 런타임에 추가·삭제할 수 없다.

**`completedAt`은 완료 목록 정렬에만 쓴다.** 완료 필터에서 최근에 끝낸 항목이
위에 오게 한다. 자동 정리 기능은 없으므로 다른 용도는 없다.

**`version: 1`은 현재 아무 동작도 하지 않는다.** 나중에 스키마가 바뀔 때 기존
데이터를 읽어 올리는 분기점으로만 존재한다.

**ID 생성에 `crypto.randomUUID()`를 쓰지 않는다.** 보안 컨텍스트를 요구해
`file://`에서 브라우저에 따라 없을 수 있다. 더블클릭 실행이 전제이므로
`Date.now().toString(36) + "_" + Math.random().toString(36).slice(2, 7)`을 쓴다.

### 정렬

- 미완료 항목: `createdAt` 오름차순 (추가한 순서대로, 오래 남은 일이 위에 머문다)
- 완료 항목: `completedAt` 내림차순 (최근 완료가 위)
- 전체 필터: 미완료 먼저, 그 아래 완료

## 4. 영속성

**모든 상태 변경 직후 전체 상태를 한 번에 저장한다.** 디바운스나 부분 저장은
넣지 않는다. 하루 10~20개면 1년을 모아도 수천 개 수준이고 JSON 전체가 수백 KB로
localStorage 5MB 한도에 한참 못 미친다. 매 변경마다 쓰는 것이 "새로고침해도
사라지지 않는다"를 가장 확실하게 보장한다.

### 실패 처리

**쓰기 실패** — 사생활 보호 모드나 용량 초과에서 `localStorage.setItem`은 예외를
던진다. `try/catch`로 잡고 화면 상단에 경고 배너를 띄운다. 침묵시키면 사용자는
저장된 줄 알고 브라우저를 닫는다.

**읽기/파싱 실패** — JSON 파싱이 깨지면 빈 목록으로 시작한다. 단, 깨진 원본을
`todolist.v1.corrupt` 키로 옮겨 보존하고 덮어쓰지 않는다. 복구 가능성을 남긴다.

**localStorage 자체가 차단된 환경** — 메모리에서만 동작하고, 상단에 "이
브라우저에서는 저장되지 않습니다" 경고를 고정 표시한다.

## 5. 코드 구조

단일 파일이지만 층 경계는 주석과 함수 범위로 유지한다.

```
index.html
├─ <style>                    전체 CSS
├─ <body>                     정적 골격
│    헤더 / 진행률 영역 / 입력 폼 / 필터 / <ul id="list">
│    <template id="todo-item">  할 일 한 줄의 마크업 원형
└─ <script>                   6개 구획
     1 CONFIG    CATEGORIES, STORAGE_KEY, MAX_LEN
     2 STORAGE   load() / save()                 — localStorage만 아는 층
     3 LOGIC     addTodo / editTodo / removeTodo / toggleTodo / clearCompleted
     4 PROGRESS  진행률 집계
     5 RENDER    render()
     6 EVENTS    리스너 바인딩
```

### 핵심 결정

**단방향 흐름, 전체 재렌더.** 이벤트 → 상태 변경 → 저장 → `render()`.
바뀐 줄만 골라 갱신하는 최적화는 넣지 않는다. 항목이 수백 개여도 재렌더는
체감상 즉시인 반면, 부분 갱신은 "상태는 바뀌었는데 화면이 안 따라오는" 버그의
주된 원인이다. 성능을 거의 내주지 않고 그 버그 부류를 통째로 없앤다.

**3·4번 층(LOGIC, PROGRESS)은 DOM을 참조하지 않는다.** 상태 객체를 받아 새
상태나 숫자를 돌려주는 함수로만 구성한다. 7장의 테스트 패널이 이 층을 겨냥한다.

**리스너는 `<ul>` 하나에만 붙인다 (이벤트 위임).** 각 줄의 체크박스·수정·삭제
버튼은 `data-action`과 `data-id`를 달고 한 핸들러에서 분기한다. 매 렌더마다
항목을 다시 그리는 구조에서 줄마다 리스너를 붙이면 리스너가 쌓인다.

**할 일 텍스트는 `textContent`로만 넣고 `innerHTML`을 쓰지 않는다.** 개인용이라도
`<img src=x onerror=...>` 같은 입력이 자기 브라우저에서 실행된다. `<template>`을
복제해 텍스트만 채우는 방식이 이를 구조적으로 막는다.

## 6. 화면과 상호작용

세로 한 컬럼, 최대 폭 600px, 가운데 정렬.

```
할 일 관리
▓▓▓▓▓▓░░░░░░░░░  7/18 (39%)
업무 3/7 · 개인 2/5 · 공부 2/6
─────────────────────────────
[ 할 일 입력...        ] [업무 ▾] [추가]
─────────────────────────────
[미완료] 전체  완료            전체 ▾
─────────────────────────────
☐ PRD 초안 검토        [업무]  수정 삭제
☐ 장 보기              [개인]  수정 삭제
☑ 알고리즘 1강         [공부]  수정 삭제   ← 취소선 + 흐리게
```

### 진행률

전체 진행률 바 하나와 그 아래 카테고리별 요약 한 줄. 퍼센트와 함께 항상
`7/18` 형태의 실제 개수를 적는다 — 퍼센트만 있으면 몇 개인지 다시 세야 한다.

분모는 해당 범위의 전체 할 일 수(완료 포함)다. 분모가 0이면 `0/0 (0%)`으로
표시하고 나눗셈을 건너뛴다.

누적 목록이고 자동 정리가 없으므로 완료 항목이 쌓이면 분모가 계속 커지고
퍼센트는 서서히 둔감해진다 (한 달 뒤 `230/310`은 오늘의 상태를 거의 말해주지
않는다). 이를 끊는 장치는 자동 정리가 아니라 아래의 '완료 비우기'다 — 데이터가
사라지는 시점을 사용자가 정한다.

### 입력

연속 투입에 맞춘다.

- Enter로 추가된다.
- 추가 후 입력창이 비워지고 **포커스가 유지**되어 바로 다음 줄을 칠 수 있다.
- 카테고리 선택은 **마지막 값을 유지**한다. 업무 할 일 다섯 개를 연달아 넣을 때
  매번 다시 고르게 만들지 않는다.

### 필터

두 축이 AND로 결합한다.

- 완료 상태: 미완료(기본) / 전체 / 완료
- 카테고리: 전체(기본) / 업무 / 개인 / 공부

필터 선택은 저장하지 않는다. 새로고침하면 기본값으로 돌아간다. 저장할 가치보다
영속 상태가 하나 늘어나는 비용이 크다.

### 수정

인라인 편집. 수정 버튼을 누르면 그 줄의 텍스트가 입력 필드로 바뀐다.
Enter로 저장, Esc로 취소. 모달은 쓰지 않는다. 다른 줄의 수정 버튼을 누르면
진행 중이던 편집은 취소된다. 편집 중 텍스트를 비우고 저장하면 저장하지 않고
원래 값을 유지한다 (삭제는 삭제 버튼으로만).

### 삭제

`confirm()` 한 번을 거친다. 되돌리기가 없는 영구 삭제이기 때문이다.
undo 토스트는 범위 밖이다.

### 완료 항목 비우기

필터 바 오른쪽에 '완료 비우기' 버튼을 둔다. **현재 카테고리 필터 범위의** 완료
항목을 모두 삭제하며, 미완료 항목은 건드리지 않는다. `confirm()`에 삭제될
개수를 적어 보여준다 ("완료한 할 일 23개를 삭제합니다. 계속할까요?").
대상이 0건이면 버튼을 비활성화한다.

자동 정리를 넣지 않는 대가로 이 버튼이 필요하다.

### 빈 상태

두 경우를 구분한다.

- 할 일이 하나도 없음 → "할 일이 없습니다. 위에서 추가해 보세요."
- 필터 결과만 0건 → "조건에 맞는 할 일이 없습니다."

## 7. 엣지 케이스와 검증

### 명시된 동작

| 상황 | 동작 |
|---|---|
| 공백만 입력 | `trim()` 후 빈 문자열이면 추가하지 않음 (조용히 무시) |
| 중복 텍스트 | 허용. 같은 일을 두 번 적는 것은 정상 |
| 200자 초과 | `maxlength` 속성으로 입력 차단 |
| 할 일 0개 | 진행률 `0/0 (0%)`, `NaN` 방지 분기 |
| 카테고리에 할 일 0개 | 해당 카테고리 요약 `0/0` |
| 편집 중 다른 줄 편집 시작 | 이전 편집 취소 |
| 완료 비우기 대상 0건 | 버튼 비활성화 |
| 완료 비우기 실행 | 미완료 항목은 영향 없음 |
| localStorage 쓰기 실패 | 경고 배너, 메모리 상태는 유지 |
| localStorage 데이터 손상 | 빈 목록으로 시작 + 원본을 `.corrupt` 키로 보존 |

### 테스트 패널

URL에 `?test`를 붙이면 페이지 하단에 테스트 패널이 열린다. LOGIC·PROGRESS 층의
순수 함수에 대한 assert를 실행하고 통과/실패를 출력한다. 실제 localStorage를
건드리지 않고 상태 객체만 주입한다. 30~40줄 규모.

최소 검증 대상:

- `addTodo`: 공백 입력 거부, trim 적용, 필드 초기값(`done: false`, `completedAt: null`)
- `toggleTodo`: `done` 반전, `completedAt` 설정과 해제
- `removeTodo`: 해당 id만 제거
- `editTodo`: 텍스트 교체, 빈 텍스트 거부
- `clearCompleted`: 완료 항목만 제거, 카테고리 범위 한정
- `progress`: 정상 비율, 분모 0, 카테고리별 집계

평상시에는 `?test`를 붙이지 않으면 패널이 나타나지 않는다.

### 수동 체크리스트

테스트 패널이 덮지 못하는 부분은 브라우저에서 직접 확인한다.

1. 할 일 5개 추가 → 새로고침 → 5개가 그대로 있다
2. 완료 체크 → 새로고침 → 완료 상태가 유지된다
3. 필터 조합 6가지(완료상태 3 × 카테고리 4 중 대표) 전환이 올바르게 동작한다
4. 빈 목록과 필터 0건의 메시지가 다르게 나온다
5. 수정 중 Esc가 원래 값을 되돌린다
6. 삭제 confirm에서 취소하면 삭제되지 않는다
7. 완료 비우기가 미완료 항목을 남기고 완료 항목만 지운다
